## (추가 5) 반응속도 개선 — 체감 1.5~2s → 0.6~1.0s

병목 실측: 소형 밴드 POST RTT 0.6~0.9s의 주범은 e-ink도 base64도 아닌 **WiFi modem sleep**이었다. 추가로 launchd 브리지가 매 POST마다 `x4-terminal.local` mDNS를 재조회하며 kevent에서 수 초씩 블록되는 문제 발견.

### 펌웨어 (xteink-terminal main.cpp, OTA 플래시 완료)

1. **WiFi.setSleep(false)** — GET /status 0.7~0.9s → **25ms**. 대가: 대기전류 ~20mA→~100mA (반응속도 우선 정책)
2. **화면 갱신 FreeRTOS 태스크 분리** — loop()는 HTTP/OTA 전담, "epd" 태스크(6KB 스택)가 그리기 담당. 리프레시 중에도 밴드 수신 가능. bmp 더티 플래그는 portMUX 임계영역, 텍스트 모드 rows[]는 mutex. framebuf 자체는 비잠금(찢김은 다음 partial에서 자가복구). OTA 시작/ WiFi 재설정 시 태스크 suspend
3. **/bandraw 신설** (HTTPRaw 스트리밍) — base64/힙버퍼 없이 framebuf 직접 기록. h 제한 없음(480행 = 전체 프레임 1 POST). 기존 /band(base64)는 구펌웨어 호환용 유지
   - 프레임워크 함정 2개: ① raw 루프의 readBytes(1436)가 마지막 청크에서 클라이언트 타임아웃까지 블록 → **바디를 1436(HTTP_RAW_BUFLEN) 배수로 0 패딩**해 우회 ② raw 시점엔 쿼리스트링 미파싱 → **밴드 좌표를 X-Band-Y/H/Full 헤더로 전달**
   - platformio.ini: espressif32 6.4.0 → **6.10.0 핀** (HTTPRaw는 arduino-esp32 2.0.12+)
4. 실측: 1행 밴드 **47~54ms**, 120행 129ms, 전체 480행 **430ms** (HTTP 204)

### 브리지 (x4_bitmap_bridge.py + mirror_daemon.sh/start_mirror.sh)

- /bandraw 우선 사용, 404면 base64 /band 영구 폴백 (구펌웨어 호환)
- **mDNS 1회 해석** (`resolve_base`) — 시작 시 IP 고정, 전송 실패 백오프에서만 재해석 (DHCP 대비)
- 폴링 0.3 → **0.12s** (양쪽 스크립트)
- raw일 때 MAX_H 120→480 (전체 프레임도 1 POST)

- 남은 물리 한계: e-ink partial 리프레시 ~0.4s + 갱신 최소간격 250ms

### 마지막 줄 "/rc" (버그 아님)

- tmux 페인 마지막 행 우측의 `/rc`는 **Claude Code TUI가 그리는 OSC-8 하이퍼링크** (`https://claude.ai/code/session_…` 링크의 표시 텍스트) — claude.ai 웹 세션 연동 표시
- 일반 터미널에선 클릭 가능한 링크지만 e-ink 미러는 텍스트만 렌더되어 낯설게 보임. 브리지/펌웨어 문제 아님 → 조치 불필요 (Ctrl-L·리사이즈 재도장으로도 사라지지 않는 것으로 확인)

### "/rc" 후속: 정체 확인 + 브리지 필터

- 정체: Claude Code **Remote Control** 표시 (claude.ai 웹/모바일에서 세션 원격 조종 링크, v2.1.128+)
- 브리지 `capture()`에서 `strip() == "/rc"` 인 줄을 공백 처리 — 기능 유지, 화면 노이즈만 제거 (줄 자체는 여전히 Claude Code가 점유)
- 줄을 되찾으려면 Remote Control 비활성화 필요: `~/.claude/settings.json`에 `"disableRemoteControl": true` 또는 세션 기동 시 `CLAUDE_CODE_DISABLE_REMOTE_CONTROL=1` / `claude --disable-remote-control` — 폰/웹 원격 조종 기능 상실과 맞교환이라 **사용자 결정 보류**
